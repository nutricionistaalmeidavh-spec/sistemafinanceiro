# E10–E13 Operations Design

## Scope

Implement roadmap deliveries 10–13 on top of the local-first desktop financial system:

- **E10 Alerts:** due today, overdue, low-balance and internal alerts with read/dismiss state.
- **E11 Receipts & reports:** settlement receipt payloads, printable HTML, CSV/XLSX export, filtered financial reports and PDF/print hooks.
- **E12 Backup & recovery:** manual/automatic backup, integrity manifest, validated restore, and pre-migration/pre-restore safety copies.
- **E13 Optional LAN:** opt-in local HTTP server, explicit LAN enablement, short-lived pairing codes, token-authenticated browser access for phone/tablet, and a lightweight responsive dashboard/entries interface.

## Constraints

- Core runtime must remain **R$ 0**, self-hosted and local-first.
- No paid service, cloud account, external database, VPS or remote API is required.
- No GitHub Actions workflow is added or triggered automatically by this delivery.
- LAN is **disabled by default** and binds to loopback until explicitly enabled.
- Restore must never overwrite the active database before validation and a pre-restore backup.
- Reports/exports must work without Microsoft Office or proprietary software.

## Architecture

### Alerts

`AlertService` derives financial alerts from existing entries and balances instead of duplicating financial truth. User-specific read/dismiss state is persisted in `alert_states`; custom internal notices are stored in `internal_alerts`. Low-balance thresholds live per financial account.

### Reports / receipts

`ReportService` reads existing finance/analytics data and produces deterministic report models. CSV is UTF-8 with BOM and semicolon separator for Brazilian spreadsheet compatibility. XLSX is generated locally as an Open XML ZIP package without a paid SDK or Office dependency. Receipt output is printable HTML; Electron printing/PDF is exposed through a dedicated document service, while the receipt model also reuses the pinned `artisys-printing` contract when installed.

### Backup / restore

`BackupService` operates on the SQLite file owned by `DatabaseService`. It uses SQLite checkpoint behavior, SHA-256 manifests compatible with the `artisys-backup` contract, retention for automatic backups, `PRAGMA integrity_check`, and a restore flow that validates first, creates a safety backup, closes the active connection, atomically replaces the database, and reopens/migrates it.

`DatabaseService` gains lifecycle helpers (`checkpoint`, `reopen`, `prepareBackup`) and performs an automatic pre-migration copy before applying migrations to an existing database.

### LAN

`LanServer` uses Node's built-in `http` module—no Express dependency. The desktop administrator explicitly enables LAN access. The service stores only hashed pairing/session credentials, returns a short-lived pairing code, exchanges it for a LAN bearer token, and exposes a restricted API.

The LAN browser UI is intentionally small/mobile-first: login by pairing code, dashboard snapshot, alerts, accounts, and payable/receivable lists. Mutations remain restricted; the first E13 implementation exposes read operations plus alert acknowledgment, preserving the PC as the authoritative writer.

## Security

- Desktop RBAC remains authoritative for IPC operations.
- Backup/restore and LAN configuration require `ADMIN`.
- LAN tokens are random, stored only as SHA-256 hashes, expire automatically, and can be revoked by disabling LAN.
- Pairing codes are single-use, expire quickly, and are rate-limited in memory.
- LAN responses do not expose database paths, password hashes, salts or desktop session tokens.

## Verification

Tests cover alert derivation/state, report/receipt/export generation, backup integrity/restore lifecycle, LAN pairing/auth/API, migration schema, and IPC permission routing. Final merge requires local service/migration verification and `node --check` for the changed CommonJS services; the complete TypeScript/Vite build is run when repository dependencies are available locally.
